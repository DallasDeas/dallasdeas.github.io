Zabbix Monitoring & Incident Investigation

I built a Windows and Ubuntu lab in Hyper-V, deployed Zabbix, and automated Gmail problem and recovery alerts. I then used monitoring records and Windows events to investigate an interruption and validate recovery.

Explore 7 evidence captures ↓Full GitHub documentation ↗
Project overview

Purpose

I wanted to practice the work that follows an availability alert: check the monitored system, verify the monitoring path, inspect the relevant events, and explain what the evidence says about recovery.

Architecture

  • Hyper-V: hosted the Windows and Linux virtual machines.
  • Windows Server: provided AD DS, DNS, and Zabbix Agent 2.
  • Ubuntu: hosted Zabbix 7.4.16, MariaDB, Apache, PHP-FPM, and Chrony, with separate internet-facing and internal lab interfaces.
  • Traffic: passive agent checks used TCP 10050; Windows later selected Ubuntu as its NTP source on UDP 123.

What I implemented

  • Validated virtual switching, static addressing, routing, DNS, and host connectivity.
  • Deployed the monitoring stack and repaired the Apache/PHP-FPM configuration.
  • Installed Agent 2, applied the Windows template, and inspected service and performance values.
  • Investigated clock skew, corrected Chrony access rules, and verified Windows time synchronization.
  • Tested Gmail delivery and configured problem and recovery operations.

October 30 investigation

Zabbix recorded the Windows agent as unavailable from 23:07:16 to 23:12:16. I compared that interval with Windows startup and service records, then checked the notification action results.

The five-minute value is the recorded problem duration. Detection latency would require a separate timestamp for the start of the underlying fault. I also kept the local service state, remote monitoring status, and notification results as separate recovery checks.

The event sequence supports a possible startup association under the documented time-zone assumption. An unexpected-shutdown message logged on October 30 described October 28, so I documented that older event separately.

Troubleshooting that mattered

  • Host connectivity: corrected the host lab adapter addressing and repeated the ping test.
  • Frontend failures: checked database readiness, web routing, and PHP handling separately.
  • Clock skew: checked the selected time source after configuration, rather than relying on command success.
  • Recovery: correlated timestamps and checked the agent, monitoring data, and notification action at their respective layers.

What I learned

A running service is only one checkpoint. I needed to verify that the next component could reach it and that the expected result appeared. The same approach helped me explain the interruption without assigning a cause that the records did not establish.

Next validation step

For a repeat test, I would capture the fault-injection time, effective trigger settings, fresh telemetry, and mailbox-arrival times so I could measure detection and notification delays separately.
